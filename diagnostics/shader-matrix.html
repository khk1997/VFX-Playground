三個階段

1. 最小 shader 階梯：從只有球體 SDF 的 baseline 開始，一次加一個 noise 相關 區塊，找出成本從哪裡開始跳升。

2. march 上限二分：如果 march=88 失敗而 march=4 正常，自動在兩者之間二分， 逼出 ANGLE 的臨界展開量。這個軸已經參數化（probe-noise-mapscene-N）， 所以能自動生成子 probe。

3. 正式 shader 階梯：從砍掉最多功能的 minshader 一路加回到完整版，看正式 shader 的成本落在哪一段。

為什麼每個 probe 都要換 shaderRun：同一份 shader 原始碼第二次編譯會命中 驅動的 bytecode 快取，量到的就不是 cold compile。shaderRun 會注入一個整數字面值 到 shader 裡（乘上恆為 0 的 uniform，畫面不變），讓每次的原始碼都不同。

四種結果的差別

OK：編譯完成，時間在偏慢門檻以下。
OK（偏慢）：編譯完成，但超過偏慢門檻。門檻附近的訊號跟失敗一樣重要， 所以不併進 OK。
TIMEOUT：iframe 還活著，但 timeout 之內沒回報完成。
CRASHED：這一頁在測那個 probe 時整個瀏覽器掛掉，重開後才發現。 最嚴重的訊號。

timeout 為什麼是 30 秒：這個值原本是 5 秒，而那讓 TIMEOUT 同時涵蓋了 「編譯器 hang」與「編譯要二十秒」兩件完全不同的事 —— 5 秒一到父頁就把 iframe 收掉，編譯被中止，我們什麼都沒量到。正式 shader 的規模是 baseline probe 的十倍 以上，所以必須給它真的編譯完的機會，才分得出是慢還是掛。

後端要分開測：Windows Chrome 走 ANGLE，而 ANGLE 底下還有 D3D11 / Vulkan / OpenGL 幾種後端，編譯器完全不同。上方的環境面板顯示這一頁實際跑在哪一個， 而進度是按後端分開存的（localStorage key 帶後端名），所以換後端不會接續 上一個後端的結果。用 start-server.bat 的參數切換後端。

遇到 TIMEOUT / CRASHED 就停：那意味著剛才那支 shader 可能已經把 GPU process 或 driver 弄到不正常的狀態，之後量到的數字快也不能證明什麼、慢也不能歸咎 給那支 shader。所以這一版不自動往下跑 —— 請完全關閉並重開 Chrome，再回來按 「開始 / 繼續」從下一個 probe 接續。

結果怎麼傳回來：由 iframe 主動 postMessage 給這一頁。 父頁直接讀 frame.contentWindow 需要同源，而那條路會在兩種情況下整批 失效 —— 這一頁用 file:// 開啟（每個 file:// document 都是獨立的 opaque origin），或 iframe 的 renderer process 掛掉變成 chrome-error://chromewebdata（那也是 cross-origin）。兩種都只會讓 父頁收到一串看不懂的 cross-origin error 而不是「這個 probe 超時了」。 postMessage 不受同源限制；真的把 renderer process 弄掛時就沒有訊息送出來， 這一頁會乾淨地判定 TIMEOUT。後端欄的「via」標示這一筆是走哪條通道拿到的。

後端的三個時間點：每個 probe 都記錄 renderer 建立後（編譯前）、編譯完成後、 以及結束當下的後端，外加 webglcontextlost / webglcontextrestored 次數。三者一致時只顯示一個值；一旦不一致就標成 「後端換過人」並全部攤開 —— 「這個 context 一開始就是軟體算繪」和「它把 GPU 弄掛 之後才變成軟體算繪」是兩件完全不同的事，只看最後一次查詢分不出來。
